## Findings

1. Source metadata is inconsistent: the top-level `source` cites Table 6.1-4, but `standard.sourceTables` and actual rows cite only 6.1-1 and 6.1-10. The deferred list explicitly excludes 6.1-4.
2. The validator treats any oversized elbow dimension outside its tolerance as a small-size floor, regardless of size or magnitude. This is not a bounded exception.
3. The specific validator does not reject duplicate dimensional keys or incorrect DN/NPS pairings. The schema permits both mutations as well: DN only has a positive-integer constraint, and the dimensions array has no keyed uniqueness rule.
4. The qualifier is an unconstrained nullable string. Unrecognized qualifiers skip the geometry check; there is no schema-level conditional relationship between fitting, qualifier, dimension and symbol.
5. Geometrical plausibility is not independent verification against a purchased source table. Caps receive no geometry check. The pack's `verified: true` is inherited provenance, not a verification performed in this review.
6. The source standard and extraction tools are not present in this transfer, limiting independent normative verification.

## Recommended continuation

First harden reference validation with failing regression tests: keyed uniqueness, DN/NPS agreement, fitting/qualifier/dimension/symbol relationships, source-table consistency, and explicitly bounded/source-cited small-size exceptions. Original source evidence is needed before changing engineering values or asserting new tolerance rules.

Then add a framework-independent or Support/Reference reader following existing reference services, with explicit no-data/unsupported/unverified responses and provenance. Wire it into PMS/model consumers only after confirming that scope. Expanding to two-size components is a separate schema/product decision, not an incidental requirement for consuming the already supplied elbow/cap data.

No application code, reference values, database schema or original handoff was changed during this review.
