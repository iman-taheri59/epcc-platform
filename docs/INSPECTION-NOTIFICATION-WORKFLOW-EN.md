## Issued-notification PDF — 2026-10-20 addendum

**IMPLEMENTED / TARGETED VERIFIED; NOT PRODUCTION DEPLOYED.** Open an **issued** notice and select **Download issued notification PDF**. Use `?lang=en` or `?lang=fa`; the endpoint is `GET /projects/{projectCode}/inspection-notifications/{notificationId}.pdf`. Drafts have no download action and authorized draft export requests receive422.

- Existing notice readers only: issuing company or explicitly selected recipients, subject to current membership, quality module/pack, discipline scope, active user and project participation. No new role, document/PO read delegation or identity-lookup escape. A configuration administrator is not automatically a notice recipient. Visibility is checked again after rendering; an independent connection revoking recipient participation during rendering is tested to prevent file return. This is not continuous authorization or universal race certification.
- Historical body comes from immutable issue data, not current ITP/stage/document, issuer/company or PO metadata. Includes number, issue time/person, original activity boundaries with offsets (or explicitly labelled legacy single time), work/location, recorded ITP number/revision/UUID, stage/point/CDE state, both entered descriptions/notes and selected recipients. Optional PO is UUID only, with no commercial data. Source/project archival or later name changes do not rewrite history. Read-only export does not change the issued record.
- **New issues** additionally capture project UUID/code/English and Persian names. Older issues are not migrated/backfilled: where the whole project metadata group is absent, print an explicit “not captured” warning and retained project UUID, not today's name/code. Partial/inconsistent snapshots are refused with422; no live-data repair/fallback.
- Actual Chromium PDFs verified in both languages; Persian uses embedded Vazirmatn and RTL text. Text is escaped, assets are local, long paragraphs flow over pages. Attachment names contain notice UUID and language only; response uses `application/pdf`, `nosniff`, `private, no-store`. A generated copy is **not** a digital signature, certified inspection, approval/release, email delivery or acknowledgment.
- Operator requirement: executable headless Chromium/Chrome plus Vazirmatn font installed and accessible to the application OS account; writable temporary directory and sufficient rendering resources. Debian/Ubuntu example: `apt-get install chromium fonts-vazirmatn`; `poppler-utils` is additionally needed for verification. Provision these in the real deployment image: sandbox package installs are not deployment evidence. Missing/failing renderer returns localized503 with no fake PDF or HTML substitute; details go to server reporting, not download output. The template has no remote assets; browser flags alone are **not** a general network sandbox, so enforce outbound isolation at infrastructure level if required.

## Delivered

A separate project inspection-notification register, not the ADR-041 inspection-result form. It covers any recorded ITP work stage requiring notification: material, site, erection or testing activity. A PO is **optional**, not the activity model. The user-selected document-revision + structured-stage foundation is implemented; no archived parallel-session ITP builder was imported.

Entry: Project → quality-entitled sidebar, Procurement or Documents → **ITP inspection notifications**, or `/projects/{projectCode}/inspection-notifications?lang=en`.

### 1. Explicit main contractor and permissions

An administrator with **existing project.configure** and current quality-module/pack access selects a participating EPC company as the project's main contractor, then explicitly assigns **draft registration** and **issue** permissions to active project members of that company. The two lists may differ or include the same person; no new inspection-notice separation-of-duties rule was invented. This is project-resource permission assignment, not a new global role, purchasing/result grant, or an owner-only nomination workflow. The existing default EPC project_manager role does not have project.configure and is not silently upgraded. A genuinely authorized non-owner configuration administrator can manage these permissions; this case is tested.

No initial main contractor or default writers are installed. Multiple EPC participants are not guessed to be the main contractor. Configuration is append-only, versioned with reason/actor/time; latest20 versions are shown and earlier ones retained. Empty permission lists revoke the relevant purpose. Changing main contractor removes old-company future issuance authority; existing issued evidence is retained. Only this authorized configuration form receives the active EPC project-member selection directory.

### 2. Record an exact ITP revision's stages

Create an ITP document through the existing document register, then copy a visible revision UUID from the notification screen into the stage form. Existing **same-company doc.issue**, original-caller **doc.view**, discipline membership, quality/document entitlement and writable project are required. There is no new stage-editor role or implicit right to edit another company's ITP. Register sequence, description in at least one language, recorded H/W/R/M point and an explicit “notification required” value. Stage rows are append-only, with unique sequence per revision; no silent stage correction/rewrite is offered.

Document revisions and stages each have independent25-row pagination, not an unbounded stage/order dropdown. All recorded stages remain reachable. Unknown/hidden/non-ITP/foreign-project references are refused. Archived source revisions cannot host new notices. **WIP/SHARED/PUBLISHED status is displayed and captured; the feature does not infer ITP approval or impose an unapproved new A-suitability gate.** Linked revision/stage data is not proof of the uploaded ITP's approval/completeness. No automatic PDF extraction, mandatory-party matrix or full ITP approval workflow is claimed.

### 3. Prepare a notice

Choose a stage requiring notification, enter work/activity reference, planned activity start and end with explicit UTC offsets (end strictly later; see activity-window guide), location, explicit eligible recipient companies and optional EN/FA notes. A same-project, same-discipline **already-visible PO UUID** may be attached. A known hidden other-buyer PO still returns404; notification permissions never switch into the buyer's context. Source actor/company/point/number/state/issue time cannot be supplied in the notification payload.

Recipients are selected explicitly, not automatically fixed by ITP assignments. They must currently participate in the project and have quality-module/current-pack entitlement for this in-system inbox; these conditions are rechecked on issue. Source document visibility is **not** delegated to recipients. Selecting a company does not promise an active individual will read it or an external message will be delivered. Existing membership, active account and current discipline scope are still required to read the inbox.

Creation produces a **DRAFT**, visible to current same-company/project members within discipline scope, not to selected counterparties. Eligible draft editing is now delivered with the current draft grant and version check; draft deletion/cancellation and issued correction/reissue are not shipped; independent issued cancellation is delivered separately under ADR-043. Failed draft input is escaped/scalar-safe and restored only for the same selected stage AND revision. Duplicate deliberate draft creation is possible; content-level deduplication is not claimed.

### 4. Issue in-system

A currently authorized main-contractor issuer opens a draft and explicitly presses **Issue notification**. POST rechecks current version, actual actor/company, participation/discipline, source visibility/type/archival/discipline, current permissions, recipients and project archive under a project advisory + FOR NO KEY UPDATE row lock. Source revision/document/optional PO/recipient records receive shared locks through commit. Revocation, a departed/unentitled recipient or stale/already-issued draft refuses issuance.

Issue atomically advances the latest draft version once and records issuer/time, issue-permission version UUID and an immutable snapshot of ITP identity/revision/CDE status/stage description/point, sender and recipient names. Record fields already retain activity/location/time/notes/source IDs. No live document/PO relationship is expanded on recipient detail: the snapshot supplies the limited inspection context, even when a recipient lacks doc.view. Snapshot text is escaped and does not include PO titles/prices/MR lines or financial journals.

Number series is **project + sender company**, e.g. `PH-14-IN-EPC-PARS-000001`. This is distinct from legacy observation IRN numbers; they are unchanged. Per-company sequence avoids counting hidden old-contractor notices when main contractor changes. Project/company sequence and project number uniqueness are enforced. Duplicate concurrent issue of the **same draft** yields one success and one stale refusal, not a second issue or duplicate delivery job. Repeated issue is not a successful-idempotent response; callers must refresh. No transport queue is created in this increment.

### 5. Recipient view

After issue, only current members of the sender company or explicitly addressed participating companies, within current project/discipline/quality entitlement, can open the notice. Counterparties cannot see DRAFTs; unaddressed PMC/owner participants do not gain blanket notice oversight from procurement privileges or configuration authority. The register doubles as the company-level in-system received-notice list. Addressing a company shares only the notice, **not generic source ITP files or PO/MR/financial reads**. Leaving the project or losing entitlement removes current access without altering historical snapshots.

## Non-effects and explicit limits

**Issued ≠ delivered email ≠ read ≠ confirmed attendance ≠ inspected ≠ PASS ≠ released/usable.** EPC notice permission does not grant inspection-result signing; ADR-041's TPI/PMC/MC/OWN independence remains. No inspection record, source allocation, MR/PO state/price, lot cached verdict or stock movement is changed by draft/issue. Ten non-notification procurement/inspection/stock/financial tables are snapshot-compared in the happy-path test.

No email/SMS/push, attachment evidence, signature verification, notification-content deduplication, issued content correction/replacement/reissue or physical receipt/hold/release workflow. Independent issued cancellation is now delivered under ADR-043. Browser print CSS is presentation, not a signed PDF/certificate. H/W/R/M is recorded descriptive point data; party-matrix mandatory recipients, lead-time24/48-hour rules, no-show waivers and permission to proceed are **not implemented or inferred**. Free-text activity references are not certified WBS/contract/weld/test-pack assignments. Stages requiring notification are entered by authorized people; completeness against actual ITP files is not automatically verified.

No mutation/backfill of old inspection records or source documents, no new PO/document SELECT policy, no SECURITY DEFINER or role seeded with default notice rights. New table RLS gives purpose-limited issued-notice sharing only. SQL guards defend source/scope/current purpose/immutability; the trusted application SQL role is not a new universal per-human database identity/signature system. Broad commit-time revocation/crash/load certification remains separate.
