## Approved scope and usage

User selected **`next_notification_scope=draft_history`**: retain complete before/after draft values, editor and time for each successful edit, with existing draft-write authority and access limited to the originating company's current authorized draft readers. Counterparties must not automatically receive earlier drafts after issuance. No new role, nomination, edit authority or public history/export endpoint was approved or added.

Open a notice's detail as an eligible **originating-company** reader → **Draft edit history**. Expand a saved version pair to see recorded editor name/UUID, editing-settings version UUID and database time. Changed editable fields show **before / after**; null is distinguished from empty text. Expand **Complete retained draft snapshots (JSON)** for full schema-versioned before/after records. Values are escaped, not executable HTML. History is ordered by version descending and independently paginated25 rows (`history_page`); all captured saves remain reachable, not latest25-only retention. Identical-content successful saves still increment draft version and retain an event, explicitly labelled as no editable content change.

No history row is created merely by draft creation or issuance. The first edit's before-image retains the baseline draft at that edit's actual version; subsequent before/after pairs preserve each saved state. Existing last-editor/time columns remain useful summaries, not a substitute for the journal.

## Evidence captured and atomicity

Forward migration `2026_10_20_120000_add_inspection_notification_draft_history.php` adds `inspection_notification_draft_history` and database triggers. An **AFTER UPDATE DRAFT→DRAFT** capture records canonical `OLD` and `NEW` in the same transaction as the successful parent edit, including edits through the existing SQL guard rather than just this controller. Before/after version must differ by exactly one and each after-version is unique for that notice. The insert guard verifies the current parent after-image/actor/settings/scope and accepts only nested parent-trigger capture; direct app-role INSERT is refused. RLS has no UPDATE/DELETE policy; an additional trigger rejects such changes if made reachable. There is no public append/backfill API.

Each event stores project/company/notice/discipline, before/after version, editor UUID and **name captured at save**, immutable editing-settings UUID and the parent's database-recorded edit time. Renaming the person later does not rewrite the captured name. An explicitly granted second company member is attributed as editor while the original creator remains unchanged. Time is the database transaction's edit timestamp, **not a separately certified commit time or electronic signature**; version is the ordering key.

Snapshot **schema_version1** explicitly lists the draft's IDs/source/creation evidence/state/version, work/location, original offset input boundaries and UTC instants, legacy single-time fields where present, selected recipient UUIDs, optional PO UUID, both notes and last-edit metadata. Stored instants are normalized to explicit UTC for stable representation. No live source/document/company/person-name joins repair historical bodies, no PO title/line/pricing/financial snapshot is imported, and future columns are not silently added to this schema. User-entered notes are retained exactly; this is not content redaction or contractual approval of them.

If validation/stale version/current permission/source checks fail, no journal row is written. If capture fails or a later trigger aborts, **both body and journal roll back**. Retrying against the still-current version produces one successful event, not evidence of the failed attempt. Existing row/advisory locks and original input/issue rules are unchanged; two independent same-version editors produced exactly one edit/event and one stale refusal in the tested schedule.

## Privacy and access boundaries

- Application reuses current active user/project membership, quality/pack entitlement, discipline scope and participation checks. Read history only when `notice.company_id == actor.company_id`; current draft-write grant is required to **edit**, not to read an already-visible company draft/history. Revoking write permission does not erase or automatically revoke legitimate historical company read access.
- Sender-company history stays readable after issue/project archival under those same reader checks, including when the company is no longer configured as current main contractor. It does not grant source doc.view or PO read access; losing source-read role does not turn stored draft evidence into a live source join.
- Selected counterparty recipients, including administrative users acting only as recipients, receive only the current issued notice snapshot/body. The controller returns no history/count/pagination data for another company. History RLS additionally enforces current project/company/participation and a matching own-company parent, so recipient raw SELECT under its own tenant context yields no rows even when it can read the issued parent. A foreign project context or departed company is also refused/hidden.
- No history data are included in PDF; the current issued PDF body, reader checks/private caching and post-render visibility check stay unchanged. The ordinary PDF of an issuing company likewise is not a full draft-history export.
- These are append-only guards and FORCE RLS under the **trusted application SQL role**, not protection against a database superuser/DDL-owner compromise, cryptographic tamper-proofing, per-human database authentication or an independent signing system.

## Existing records and rollout

Migration creates an **empty journal**, not fabricated rows for old edits, and does not change existing draft/issued records, snapshots, versions, numbering or grants. On every history panel, coverage text states that changes predating installation were not reconstructed. Earliest captured before-version is displayed where available: a first event v3→v4 does **not** invent v1→v2 or v2→v3. An empty journal is not proof that an older draft was never edited. This closes full recording for **future successful saves**, not recovery of unknowable earlier versions.

Test-only prior-schema reconstruction preserves parent guards/RLS, reproduces old successful saves without this journal, installs the actual forward migration and verifies the first later capture begins at the real version. A separate populated archived-project upgrade preserves old issued/draft bodies exactly and creates no backfill/defaults. Historical fixture tests were adjusted to drop/recreate the new dependent history table when deliberately reconstructing older schema, not to disable runtime history protection.

Roll out the migration **before the matching UI/service reader code**; new code requires the table. Once installed, the database trigger captures compatible existing writers automatically. No input payload change, new JS control or user permission grant is required. down() deliberately refuses deleting retained history; follow the project's normal backup/release procedure. No production migration/deployment, retention purge, backup/restore certification or policy for issued cancellation/replacement is supplied.
