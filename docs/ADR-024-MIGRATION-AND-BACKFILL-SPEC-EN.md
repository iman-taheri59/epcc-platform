## 1. Concrete implementation boundary

First persistence increment must support exact same-document/same-pinned-scope replacement without rewriting accepted snapshots. It must also make unresolved overlap visible; do not enable an unrestricted aggregate merely because a migration succeeds. The isolated selection prototype blocks changed scope sets/versions conservatively; that restriction is not a newly approved business prohibition.

No migration file was placed in `app/database/migrations`. New executable files are dependency-free offline design/review tools. They cannot connect to the application DB, validate human authority or apply a plan.

## 2. Proposed logical relations and constraints

Names below are provisional. UUIDs are generated by the future writer, never inferred from document numbers/codes. All project-scoped relations require project FKs, same-project composite reference checks, forced RLS and archive-write guards from day one.

| Relation | Required content | Required invariants |
|---|---|---|
| `mto_acceptance_clocks` | project PK, next new-write ordinal | Only mutable counter; serialized under project lock; ordinal allocation and snapshots in same transaction; no reuse of committed ordinal |
| `mto_acceptance_provenance` | id, project, exact batch/document/revision, origin NEW or LEGACY_RECONCILED, new ordinal nullable, reconciliation-package reference nullable, captured actor/company/time | One sidecar per batch; exact source tuple FK; NEW requires positive unique project ordinal; LEGACY requires controlled reconciliation reference and **no invented global ordinal**; immutable |
| `mto_scope_manifests` and entries | project, batch, hierarchy identity, controlled topology reference, covered stable scope IDs, immutable ancestor/membership proof, source/admission references | Exact batch/project FK; unique batch/scope; no missing/guessed scope; validate authoritative membership, header bounds and row containment; all sealed with acceptance transaction |
| `mto_effective_selection_events` | project, document, pinned scope/version, exact batch, previous event, scope-local step, transaction group, origin/provenance, actor/time | Exact covered-scope FK to manifest; same-key predecessor FK; unique root and predecessor; step1 iff root, otherwise prev.step+1; selected acceptance must advance under validated source chronology; append-only |
| `mto_additivity_events` | project, ordered canonical batch-pair, grant/revoke action, prior event, admitted controlled evidence reference, reason, provenance | Left<right, no self-pair; both exact accepted batch/project FKs; one linear append-only lifecycle per pair; every grant has admitted evidence; revoke does not delete evidence or inherited history |
| `mto_backfill_runs` and findings/resolutions | project, inventory digest, source versions, package digest, tool/schema versions, actor/admission references, run events and findings | Stable idempotency key for exact source+package+tool contract; insert-only audit; no updating accepted source or old findings to hide resolution; resolution links prior finding |

### Constraint mechanics

- Existing source tables mainly have UUID-only FKs. Add reviewed unique composite keys such as `(project_id,id,mto_document_id,mto_revision_id)` on batches before referencing those tuples. Add parent composite keys where needed for document/revision identity. Do not pretend several independent UUID FKs establish a same-project relationship.
- Selection predecessor FK must bind the **same project/document/scope/hierarchy key**, not just previous UUID. A trigger validates step and strictly advancing acceptance/legacy document-chain order. Unique partial root index plus unique nonnull predecessor prevents roots/branches. Strictly increasing local steps prevent cycles. Scope-local steps are journal structure, not reconstructed historical project-wide chronology.
- Manifest sealing requires a deferred constraint trigger or an equally reviewed transaction-group invariant: no committed manifest, snapshot sidecar or selection group may be partially populated. A unique key alone does not prove completeness. Do not add an UPDATE-based seal to accepted rows.
- Immutable relations reject UPDATE/DELETE through restrictive RLS and a DB trigger, including privileged writers. The mutable clock has tightly bounded updates, not a blanket append-only trigger. FK deletes use RESTRICT, not cascades that erase history.
- Forced project RLS follows current participant/context boundaries without broadening deferred MTO human rights. Archive restrictions apply to **all new write tables**, not only the old migration's static table list. New human endpoints remain out of scope until authority is explicitly resolved.
- Admission verification must use retained exact CDE/external evidence and approved resolver policy, not a nonempty reference from JSON. The offline planner does not implement this adapter.

## 3. Acceptance transaction and read protocol

Proposed lock order for all new acceptance/backfill writers: project row FOR UPDATE → project acceptance clock → document → revision → ordered affected selection keys. Reject archived project inside the project lock; existing archive updates contend on that same project row. Re-read draft/source rows under lock, validate controlled scope/admission, allocate NEW ordinal, create accepted batch/rows, create sidecar+sealed manifest+selection group and update source revision in **one transaction**. Roll back everything on any failure. Different-document acceptance is serialized per project initially; optimize only after correctness evidence.

A next accepted revision must replace complete covered scope snapshots, not individual material rows. If scope set/version changes and disposition is unavailable, selection readiness is blocked, not silently carried or cleared. Backfill cannot introduce a historical selection after a concurrent new acceptance without re-inventory/revalidation.

Reports use one repeatable-read snapshot for heads, admitted pair-event heads, scope graph and quantities. Include selection/evidence versions in report/caches. Revoke makes current reports unresolved where needed; historical reports retain their cutoff/version. Existing engineering-estimate links remain historical and are not relinked by backfill.

## 4. Legacy inventory and reconciliation protocol

### Phase A — collect without writing

Export one project's accepted batches and exact rows from a consistent **read-only, tenant-bound** transaction, recording export cutoff, tenant context, source count and canonical digests. Export all accepted revisions in scope, not just a preferred winner. No customer data into a public demo.

Include exact project/document/revision/batch/row UUIDs; accepted time normalized to UTC with six fractional digits; snapshot hashes, quantities/units, original scope/hierarchy pins and source file provenance. Preserve original quantity text; no float normalization. The offline tool's fixture schema is an illustration, not an implemented DB exporter.

Current historical rows do not establish a complete covered scope manifest or retained topology. A row-only distinct scope list is an observation, **not proof of complete coverage**. Missing scope/hierarchy/topology remains a finding. A retained controlled package may later provide a sidecar resolution; it must not overwrite historical nulls or rewrite history.

### Phase B — review package bound to inventory

Require project + inventory SHA-256 + exact batch chain per document, reason, controlled evidence and verified authority/provenance. Even distinct timestamps do not automatically authorize historical project-wide commit order. Equal timestamps never use UUID, revision-code order or guessed MAX. Where retained acceptance evidence cannot establish a winner, leave the document unresolved.

Legacy chains establish document/scope lineage; they do **not** allocate fabricated historical global clock ordinals. New writes start their own serialized NEW ordinal stream after controlled cutover. Initial new heads may succeed a reconciled legacy head under the explicit origin/ordering rules.

Resolve scope changes with an explicit package for carry-forward, retirement or replacement and affected row IDs. A cross-version mapping is not additive evidence. Full handling is a release blocker, not an excuse to copy the prototype's fixed-scope restriction into product requirements. Pair-evidence grants/revocations need controlled admission and append-only history; no inheritance to later revisions.

### Phase C — plan and dry run

The offline planner binds the exact inventory to a proposed reviewed document chain. It detects missing identity/pins/manifest/topology, tied timestamps, stale/foreign packages, incomplete or duplicate orders and changed scope sets. It emits **BLOCKED** or **CANDIDATE_FOR_CONTROLLED_REVIEW**. Both always have `ready_to_apply=false` and `writes_performed=0`.

A candidate does NOT certify scope topology, material/unit validity, additive admission, signatures, actor rights, RLS or absence of overlap. Those are mandatory separate preflight gates in the future apply path. Blocked plans expose no partially applicable chain. Nonempty reference strings are not trusted admission.

### Phase D — future controlled apply (NOT implemented)

Enter a per-project maintenance/cutover window; take the project/clock locks. Re-export and recompute **both inventory and candidate package digests** under the write transaction. Compare source identities, row counts and hashes to the reviewed package. Reject any drift; do not merge a stale plan. Verify package evidence and authority independently. Recheck active project, tenant, manifests, topology, all-pair overlap/additivity, journal roots and existing sidecars.

Apply all accepted sidecars/manifests/selection chains for the project atomically or none; never skip a conflicting document and call the remaining report ready. Repeated identical apply must return the existing run and verify all inserted content, not duplicate it. Same idempotency key with different content is a hard error. Test interrupted transactions and retries before release.

Archive projects stay read-only. Do not grant a migration tool a hidden archive bypass; any separately authorized archival reconciliation process needs explicit policy. No role design is inferred here.

## 5. Rollout and rollback without history destruction

1. **Expand:** add empty new relations, functions, guards and indexes with the old board path unchanged. Inventory existing FK/identity anomalies first. Evaluate lock durations on a restored production-like copy; concurrent index operations need a separate nontransactional deployment step when appropriate.
2. **Shadow:** run candidate selection side-by-side, report differences and unresolved reasons; no procurement decisions from shadow values. Ensure unpublished/stale net references remain visible.
3. **Reconcile/backfill:** controlled packages only; no timestamp/UUID guessing, no mutation of accepted tables. Keep feature disabled for unresolved projects.
4. **Enable:** only after real DB concurrency/rollback/tenant/archive tests and UI/API unresolved-state handling pass, followed by related app regressions, full suite and integrated pilot.
5. **Rollback:** disable the new read path and new acceptance writer together; preserve append-only new data. Do not silently fall back to the old misleading aggregate for a previously unresolved project. Show unavailable/manual-reconciliation state. A destructive down migration is not an operational rollback after data exists.
