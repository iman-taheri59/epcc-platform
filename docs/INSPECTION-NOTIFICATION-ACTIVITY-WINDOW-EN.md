## Accepted requirement and decision

User requires the period for performing the inspected activity on its notification. The explicit choice is **`activity_window=replace_time`**: replace the single proposed inspection time in new registration/draft saves with **planned activity start and end**. Do not retain a second mandatory inspection appointment or add an appointment-inside-window rule. This supersedes the former single-time input contract only; it does not authorize rescheduling or rewriting an issued notice.

## Use and contract

1. Select the ITP stage and register a draft, or open an eligible draft's **Edit draft** form.
2. Enter **Planned activity start** and **Planned activity end**, both required. The fields use Gregorian date-times with seconds and explicit offsets, for example `2026-10-25T09:30:00+03:30` and `2026-10-25T11:30:00+03:30`. No server/browser time zone is guessed. Named time zones or an automatic Jalali calendar conversion are not provided.
3. End must be **strictly later in absolute time**, not simply lexically later. Different offsets, midnight crossings and an offset change can be valid. Equal instants, zero-length/reversed intervals, missing offsets, impossible dates and nested/partial input are refused with422. No maximum duration, overlap prohibition, business calendar, lead-time/hold/waiver/proceed or actual-execution certification is inferred.
4. Both recorded boundaries appear in EN/FA register, details and PDF. Issued boundaries are immutable; selected recipients see the same recorded values with original offsets. A planned range is not proof of when inspection/activity actually happened.

The existing POST/PUT endpoints now require `notification.activity_start_at` and `notification.activity_end_at`; the strict payload rejects the former `notification.scheduled_at`, even when supplied alongside the new fields. Stage/revision/work/location/recipients/optional PO/notes and optimistic version rules are otherwise unchanged. Each boundary is retained as original `activity_start_input` / `activity_end_input` plus normalized UTC `activity_start_at` / `activity_end_at`. New-window records have **null legacy single-time columns**, not a fabricated inspection appointment equal to start. The issued immutable row, not a live join, holds the recorded activity window.

## Existing records — no fabricated history

- **Previously issued notices:** no backfill or content/snapshot rewrite. New window columns remain null, the original single time stays unchanged. Detail/register/PDF explicitly label it **Legacy proposed inspection time (single time)** and state that no activity execution window was recorded. An end is never inferred from the old time, a default duration or end-of-day. This also works on an archived project and with older snapshots lacking project names.
- **Existing legacy drafts:** remain readable with their labelled old single time. Their edit form starts with both new boundaries blank; it never copies the old appointment to start/end. A currently authorized person must explicitly save both boundaries with the current draft version. That ordinary versioned edit clears the old single-time fields, records last-editor evidence and preserves original creator/source. Only then can the draft be issued using its new version. Until conversion, the issue action is hidden and direct service/SQL attempts are refused; legacy-shaped new inserts are refused too. This is deliberate draft conversion, not an issued-history migration.

## Authority, migration and operations

Existing independent main-contractor draft/issue grants, current participant/active-user/quality-pack/discipline/doc.view/source checks, optional original-visible PO, project writability, row/advisory locks, stale protection and immutable issued evidence remain. No new role, read delegation, endpoint, stock/MTO/MR/PO mutation or result-recording authority. Draft edits remain fixed-source; latest-editor columns now have a separate append-only before/after journal for future saves, without reconstructing pre-install revisions.

Forward-only migration `2026_10_20_110000_add_inspection_notification_activity_window.php` adds four nullable window columns, permits null old single-time columns, and constrains each row to a **complete ordered window with no single time**, or **a retained complete legacy single time with no window**. It replaces the trigger function to require a window for new inserts, draft edits and all future issuance, validate offset strings against stored UTC instants and admit only the existing explicit mutable draft fields plus window fields. Issued edits/deletes/source rewrites remain blocked. The previous migrations are untouched; FORCE RLS/policies are unchanged. No row UPDATE/backfill/default grant is run by the migration. down() refuses destructive conversion of a range to a single time.

**Coordinate application + migration + clients/workers as one release.** This is an intentional payload change: old writers using only `scheduled_at` will be rejected after migration, and new code requires the new columns. Pause/drain writes during deployment according to the project's normal backup/release procedure; do not claim mixed-version write compatibility. No production release/migration was run here.
