# رجیستریِ گاردها — متنِ هر گارد کجا زندگی می‌کند (فارسی)

> وضعیت: پیاده‌شده ۲۰۲۶-۱۰-۲۹. تصمیم: [`ADR-059`](ADR-059-GUARD-SQL-SINGLE-SOURCE-EN.md).
> English twin: [`GUARD-SQL-REGISTRY-EN.md`](GUARD-SQL-REGISTRY-EN.md).

## گارد چیست

چهل‌وهشت تابع به نامِ `epcc_guard_*` نوشته‌هایی را رد می‌کنند که یک ناوردا را
می‌شکنند: رکوردِ custody که نباید بازنویسی شود، تصمیمِ QA که باید به مدرکی که به
آن استناد کرده گره بخورده باشد، نتیجه‌ای که باید توسط کسی که پروژه واقعاً نامزد
کرده ثبت شود، lot قدیمی‌ای که نباید بی‌سر و صدا به lot کنترل‌شده ترجمه شود. این‌ها
بخشی از پلتفرم‌اند که می‌گویند **نه** — و همان بخشی که باید با دقت خوانده شود،
چون آنچه رد می‌کنند در واقع مشخصاتِ سیستم است.

## مسئله‌ای که حل شد

هر گارد در مایگریشنی که معرفی‌اش کرده بود، inline اعلام می‌شد. وقتی یک برشِ بعدی
نیاز داشت یک IF از یک گاردِ موجود را تغییر دهد، تنها حرکتِ ممکن این بود که
**کلِ بدنهٔ تابع** را در یک مایگریشنِ جدید بازاعلام کند — بایت‌به‌بایت یکسان،
به‌جز همان یک خط. وضعیت امروز:

| گارد | تعداد محلِ اعلام |
|---|---|
| `epcc_guard_notification` | ۳ مایگریشن |
| `epcc_guard_piping_grn` | ۲ (نسخهٔ A.4f فقط یک IF را عوض کرد) |
| `epcc_guard_material_certificate` | ۲ |
| `epcc_guard_joint_result` | ۲ |
| `epcc_guard_piping_qa` | ۲ |
| `epcc_guard_piping_receiving_review` | ۲ |
| … و بیش از ده موردِ دیگر | ۲ تا |

این نسخه‌ها باید با دست هم‌تراز نگه داشته شوند، و **انحراف بی‌صداست**: پایگاه‌داده
در نهایت چیزی می‌گوید که هیچ فایلِ واحدی در مخزن آن را نمی‌گوید. خواندنِ یک
مایگریشن به شما می‌گوید آن گارد **در آن زمان** چه می‌گفته، نه اینکه **الان** چه
می‌گوید — و تنها راهِ دانستنِ متنِ فعلی این بود که از یک پایگاه‌دادهٔ در حال اجرا
بپرسید.

## قانون از امروز

**`database/guards/<name>.sql` تنها جایی است که متنِ فعلیِ یک گارد در آن زندگی
می‌کند.** هر گارد یک فایل؛ هر فایل یک عبارتِ کاملِ `CREATE OR REPLACE FUNCTION`،
گرفته‌شده از `pg_get_functiondef()` — یعنی دقیقاً همان چیزی که پایگاه‌داده همین
الان اجرا می‌کند.

- **برای تغییرِ یک گارد، فایلش را ویرایش کنید.** آن را در یک مایگریشن بازاعلام
  نکنید.
- **مایگریشنی که با `CREATE TRIGGER` گاردی را متصل می‌کند، باید درست پیش از آن
  `GuardSql::apply($name)` را صدا بزند**، تا تریگر حتی در صورتی که فایل در همان
  تغییر ویرایش شده باشد، متنِ فعلی را ببندد.
- **گاردِ جدید** به‌شکل یک فایل اضافه می‌شود، سپس به همین شیوه اعمال و متصل
  می‌گردد.
- نام‌ها اعتبارسنجی می‌شوند (`^epcc_guard_[a-z0-9_]+$`) چون نام تبدیل به مسیر
  می‌شود.

نسخه‌های تاریخی در مایگریشن‌های خود باقی می‌مانند — آن‌ها همان چیزی‌اند که
پایگاه‌داده با آن‌ها ساخته می‌شود — اما مایگریشنِ
`2026_10_29_200000_consolidate_guard_definitions.php` پس از همهٔ آن‌ها، هر ۴۸ فایل
را اعمال می‌کند، پس **حرفِ آخر را فایل‌ها می‌زنند**.

## استفاده

```php
use App\Support\GuardSql;

GuardSql::apply('epcc_guard_piping_grn');   // یک گارد، پیش از CREATE TRIGGER
GuardSql::apply(['a', 'b']);                // چند گارد
GuardSql::apply();                          // همه

GuardSql::names();                          // رجیستری، مرتب
GuardSql::body('epcc_guard_piping_grn');    // عبارتِ کانُنیکی
GuardSql::installed();                      // نام => pg_get_functiondefِ نصب‌شده
GuardSql::definitionOf('epcc_guard_x');     // تعریفِ یکی، یا null
```

## چه چیزی آن را اعمال می‌کند

`tests/Feature/GuardDefinitionsTest.php` (۶ تست / ۱۵۰ assertion):

1. رجیستری غیرتهی است و هر فایل نامِ درستی دارد؛
2. مجموعهٔ فایل‌ها برابرِ مجموعهٔ گاردهای نصب‌شده است — نه فایلِ یتیم، نه تابعِ
   ثبت‌نشده؛
3. اعمالِ دوبارهٔ همهٔ فایل‌ها هیچ چیز را تغییر نمی‌دهد — یعنی یک پایگاه‌دادهٔ
   تازه‌مایگریت‌شده همین حالا هم با رجیستری موافق است؛
4. هر فایل به‌تنهایی SQL ی معتبر و idempotent است؛
5. **هیچ مایگریشنی با تاریخِ پس از پاسِ یکپارچه‌سازی، گاردی را inline اعلام
   نمی‌کند** — این همان assertion ی است که قانون را واقعی می‌کند نه آرزو؛
6. هر گاردِ ثبت‌شده واقعاً به یک تریگر متصل است (چیزی یتیم نمی‌ماند).

## چرا الان، و چرا قبل از این ممکن نبود

یکپارچه‌سازی یعنی جایگزین‌کردنِ بدنهٔ توابع در یک پایگاه‌دادهٔ نصب‌شده. مالکِ
پروژه اعلام کرده که **هیچ پروژه‌ای تاکنون با این نرم‌افزار ثبت نشده است**، پس
پایگاه‌دادهٔ نصب‌شده‌ای وجود ندارد که باید دست‌نخورده منتقل می‌شد. این پنجره
الان باز است و با نخستین پروژهٔ واقعی بسته می‌شود.

فایل‌ها از پایگاه‌دادهٔ در حال اجرا **استخراج** شده‌اند، نه بازنویسی — برای همین
پاسِ یکپارچه‌سازی بر اساسِ ساختار یک «بی‌اثر» است: رفتار تغییر نکرده، و اجرایِ
رگرسیون همین را می‌گوید.
