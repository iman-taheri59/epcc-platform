**Date:** 2026-09-30. **Status:** MR-01 and MR-02 user-confirmed; scoped draft-entry implementation in §6. Earlier pending statements in §§2–4 are historical and resolved by §5. Full lifecycle remains incomplete.

## 2. Verified source gaps, not runtime exploit claims

1. ProcurementService.raiseRequisition exists, but MaterialsController and routes expose register reading, requisition state advancement and forecasts, not request creation. A normal user cannot start a request through the current procurement screen.
2. raiseRequisition checks buyer company type (EPC/SUB/OWN), not a dedicated project human author capability. AuthorizationPipeline has no procurement-specific module/capability mapping and seeded roles have no clearly designated MR author capability. Company eligibility alone is insufficient to decide which project users may create spend requests. PMS author nomination and technical material-definition reviewer authority must not be silently reused as MR permission.
3. Entry validation must cover the real decimal(18,3) bounds without silent rounding, field lengths, project-bound subsystem selection, text types and atomic rollback. No canonical conversion or automatic MTO link should be fabricated by the new UI.

The initial announcement that implementation would start with MR creation is narrowed by finding 2: settle the new human write surface before enabling it. No new role grant or endpoint has been created.

The intended first slice is entry, not RFQ/PO/receipt/return closure. No automatic approvals, order creation or source-baseline consumption.

Planned eventual acceptance: actor/project/company/entitlement/archive checks, own-company attribution, source quantity/unit preservation, bounded multi-line validation, atomic creation, unchanged approvals and authenticated FA/EN form/old-input/XSS regression. No tests for an unimplemented feature are claimed.

## 5. MR-02 accepted and bounded implementation design

User selected `owner_project_configure`: owner-company administrator with existing project.configure capability configures nominees. No new role grants. Implement independent append-only MR author policies (not shared PMS nomination) with reason/version/actor, no initial policy; latest suspension revokes creation. Nominees limited to active project members of participating buyer companies OWN/EPC/SUB. Live company-role membership, entitlement to proc and project pack, and requested discipline scope are additional entry gates.

New web entry facade uses the existing ProcurementService as a lower-level persistence primitive under its own project-scoped transaction, authorization and shared MR-policy advisory lock. Existing internal fixtures/legacy primitive calls are not retroactively made human RBAC endpoints; only the new authenticated authoring surface is exposed. Capture policy ID on the new MR, retaining null on legacy records. No technical/commercial permission changes. New request creation is DRAFT only, with server actor/company/project/number. Policies and policy attribution immutable; existing MR transitions remain separate.

Bounded multi-line form (1–20 nonempty rows, blank rows omitted), bilingual titles/descriptions, source item code/unit/specification and optional same-project subsystem. Quantities plain positive decimal strings fitting numeric(18,3), no float rounding/exponent/fraction input. Add nullable source_quantity string to retain exact new input spelling; unit already stored verbatim. No automatic canonical conversion: existing native-unit storage remains; full ADR-014 conversion across downstream consumers is NOT closed here. No MTO baseline link fabricated. Atomic MR+items+policy/source capture; active-project service gate plus existing SQL archive backstop. Idempotent request tokens are not added; successful POST redirects, but independently repeated valid posts can create another draft.

Acceptance: configuration role/company/version/history, no default or inherited PMS access, role/user revocation, reader/nominee FA/EN form, validated row boundaries and same-project allocation, actor-spoof refusal, draft/source-policy attribution, late rollback and unchanged legacy procurement/warehouse workflows. First slice does not deliver PO/receive/returns/RFQ or a complete material lifecycle.

### Implementation defect found before multi-company activation

The old allocator locks the project but computes max(sequence) over company-filtered MR rows. Owner/EPC interleaving can collide despite serialization. Preserve the existing project-wide numbering contract using a monotone project counter under the same row lock, shared by the legacy primitive and new entry facade. Migration initializes from the union of company-visible maxima, including archived projects; no RLS disabling or record-visibility expansion. It does not reuse deleted numbers after activation. Counter initialization cannot recover already-deleted historical numbers. This is a correction of the existing contract, not a new approval decision.

## 7. PO-line scope attribution for MTO shortage roll-ups — accepted design (2026-10-02)

**Status: user-confirmed design; not implemented.** To calculate order gaps at piping-class, subsystem, system and process-unit levels while exact MTO-row↔MR lineage remains deferred, every future PO line must be attributable to the material-library item and its consumption scope (process unit, system, subsystem and piping class, where applicable). This is a scope tag, not a direct MTO-row link; the MTO header's MR number remains informational only for now.

A line with missing or ambiguous scope remains unallocated and is excluded from scoped shortage claims until resolved; do not guess, prorate automatically, or count it against multiple scopes. This decision does not add these fields to the delivered MR-entry form or claim current PO creation/issue entry exists. Physical data storage/derivation, allocation UI, amendment/cancellation behavior and acceptance tests remain design/implementation work. ADR-005 §8 defines unit-compatible comparisons; ADR-014 §15 defines when pipe branch count may be compared to length.

## 9. Gross-MTO order-gap comparison — accepted design (2026-10-02)

Compare the accepted gross procurement quantity in MTO with valid net PO quantity for the same material/scope/compatible unit. A PO quantity above gross MTO is reported separately as above-plan procurement, not as negative shortage; do not automatically amend or cancel the PO. This is a design decision only: PO entry/calculation is not implemented by this record. For comparable gross MTO and net engineering need, any positive amount by which gross MTO is below net need is a purchase-plan shortage; no project tolerance may hide it. If gross MTO is equal to or above net need, display the difference as a quantity only, without inferred percentage/cause, and do not label it excess PO. If no accepted MTO exists for the matching unit/category/scope, show a model/isometric/manual net-need estimate as provisional, not as an official order-gap baseline. Apply this per scope/category. Net physical need and the deferred usable-stock state rule remain distinct. See ADR-005 §8.

### 9.1 Gross-MTO-to-net-estimate row identity — accepted 2026-10-05

For the gross-MTO-versus-net-need comparison, pair only by the exact composite identity: project-scoped MTO source document/sub-MTO + its accepted revision or immutable batch identity + `mto_item_no`. The row number alone is not assumed globally unique; unmatched estimates stay unmapped, without description-based inference or a row-specific shortage claim. The model/engineering record must retain a stable reference to the exact immutable accepted MTO row, resolving the complete identity; the user selected a direct FK/reference to the stable identifier of the exact immutable accepted MTO row, targeting a separate accepted-row snapshot store; DRAFT rows remain in staging and cannot be FK targets. Keep `mto_item_no` for display, not as the sole join key. Snapshot rows are immutable and resolve the full composite identity. Acceptance is all-or-nothing per one MTO document/sub-MTO revision: validate every row in that submission, create all immutable accepted-row snapshots and mark only that batch accepted in one transaction; any validation/snapshot failure rolls back all snapshots and leaves that batch DRAFT. Sibling MTO documents/sub-MTOs are independent; accepting one does not close another's coverage gap. Physical table/column names and transaction implementation remain to be designed. This does not create MTO-row↔MR/PO linkage. See ADR-005 §8 and ADR-006 §10.8.

### 9.2 Aggregation across distinct MTO documents — accepted 2026-10-05

Sum gross quantities from different accepted MTO documents/sub-MTOs only when scopes are disjoint or an explicit additive relationship is recorded between the exact immutable accepted document revisions. The pair-level declaration must include a written reason and, when document-based, cite the exact immutable project-document revision—not only its document number or title. When registered in project CDE, store a stable reference to the exact CDE revision; number/title are display-only. For a source outside CDE, use a controlled external-evidence record with stable ID, issuer/source, exact document number/revision/date and retained original file or controlled immutable URI plus content hash; hash alone is insufficient. If the exact version cannot be retained and retrieved, it cannot support the additive declaration and the overlap remains ambiguous. It applies only within overlapping scope and to rows matching on material-library identity and compatible units; unresolved rows remain ambiguous/unallocated. Without a declaration for overlapping comparable scope, do not auto-sum. New revisions do not inherit the relationship automatically. Additive declarations are append-only; corrections or withdrawal require a new superseding record, not editing/deleting history. Historical roll-ups retain the relation state known at calculation time; current roll-ups use the latest effective record, and withdrawal leaves overlapping scope ambiguous/unallocated. Revisions of one document follow ADR-005 §2.2 and are not additive historical batches. Cross-version scope mappings are a separate, append-only decision: exact source/target scope IDs and tree revisions, relationship type, rationale and exact document evidence when applicable; one-to-one continuity requires equivalence evidence, while split/merge requires complete non-overlapping correspondence. A mapping does not replace additive declarations between exact MTO revisions. Historical roll-ups preserve mapping state known at calculation; current roll-ups use the latest effective direct mapping, while withdrawal leaves current allocation unresolved without rewriting history. Do not infer transitive chains unless stable IDs and pinned hierarchy revisions already establish equivalence. This does not create MTO-row↔MR/PO linkage. See ADR-005 §8.

### 9.3 Parent/child scope overlap — accepted 2026-10-05

An MTO scoped at a parent process-unit/system level overlaps descendant system/subsystem MTOs; their quantities are not added absent an explicit additive declaration. Distinct/disjoint leaf subscopes can be summed at a parent roll-up. Piping class is an independent grouping dimension, not a physical hierarchy node. See ADR-005 §8 and ADR-008 §11.20.7.

### 9.4 MTO header/row scope attribution — accepted 2026-10-05

Store physical scope at the MTO document/sub-MTO header only when all its rows share that scope; rows inherit it. If a document mixes physical scopes, state the scope on each row. A row-level descendant scope may refine the header's parent scope; a scope outside the header boundary is a conflict and remains unallocated. Missing or ambiguous row scope remains unallocated and is excluded from cross-scope roll-ups; do not guess. Scope follows process unit/system/subsystem, with piping class as an independent grouping dimension. If a required row scope is missing/ambiguous or conflicts with the header boundary, block acceptance of the entire document/sub-MTO revision; keep that batch DRAFT and create no partial accepted-row snapshots. Correct and revalidate under the existing all-or-nothing rule; sibling MTOs remain independent. Resolve scope by stable ID in the authoritative project hierarchy, not free text as operative identity; immutable accepted-row snapshots preserve the exact scope reference and later hierarchy changes do not rewrite historical assignments. User accepted pinning the hierarchy revision in each MTO snapshot; never recycling IDs; preserving acceptance-time labels/paths for display; and allowing cross-version roll-ups only where pinned relationships prove the common scope, or via an explicit immutable mapping/evidence record. See the numbered rules in ADR-005 §8 and ADR-008 §11.20.8. These rules and the acceptance gate are not implemented.

### 9.5 Physical process-unit restructuring and MTO coverage — accepted 2026-10-06

A display rename preserving the stable process-unit ID preserves its category scope. A split, merge or replacement creating new process-unit IDs does not automatically transfer the prior unit's category declarations or accepted-MTO coverage; each successor unit requires its own versioned category-scope confirmation and per-category ACCEPTED MTO or explicit out-of-scope record. A scope mapping alone does not close successor-unit coverage. Until confirmed, coverage remains unconfirmed—not zero or complete. See ADR-005 §8 and ADR-008 §11.20.3. Accepted design; not implemented.

### 9.6 Roll-up calculation provenance — accepted 2026-10-06

Each saved historical roll-up is an immutable calculation snapshot containing the exact accepted MTO revisions/rows, scope hierarchy revisions, effective mapping and additive-declaration records, material identity and unit/conversion basis, calculation time and rule version. Preserve the computed result together with provenance and separately identify unresolved/unallocated inputs and reasons. Historical results are not edited or silently recalculated; a new calculation creates a new snapshot. Current roll-up is recalculated from the latest effective inputs, with unresolved amounts kept separate and never treated as zero. See ADR-005 §8 and DR-12. Accepted design; not implemented.
